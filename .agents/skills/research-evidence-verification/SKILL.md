# Research Evidence Verification & Audit Integrity

## Purpose & Scope

This skill governs the development, debugging, validation, and empirical auditing of the evidence verification engine in `research_crew`. It guarantees that research reports generated by the multi-agent system are factually grounded, rigorously cited, and verified without false support or lenient grading.

---

## Architectural Reference

The verification pipeline consists of four tightly integrated layers:

```
[Report Markdown]
       │
       ▼
1. Citation & Mapping Layer (`validator.py`)
   ├── `extract_report_source_mapping`: regex-based bibliography resolution supporting [1], [arXiv-2401.123], [named-key]
   └── `audit_report_sources`, `audit_report_metrics`: baseline checks, metric consistency
       │
       ▼
2. Claim Extraction Layer (`verifier.py`)
   ├── `extract_atomic_claims`: splits sentences, decomposes clauses and parentheticals
   └── Links `AtomicClaim` to citation markers and resolved URLs
       │
       ▼
3. Evidence Retrieval & Passage Selection Layer (`store.py`, `verifier.py`)
   ├── `EvidenceStore`: in-memory & on-disk cache of `EvidenceRecord` (URL, full text, status)
   └── `find_passage_for_url_and_query`: extracts optimal 1,200-character context window based on empirical scoring
       │
       ▼
4. Verdict Evaluation Layer (`verifier.py`)
   ├── Entity & Acronym Grounding: token filtering, acronym recognition (`[A-Z0-9]{2,}`)
   ├── `_verify_via_mesh_llm`: prompt-guided NLI judge via configured Mesh API LLM
   ├── `_verify_heuristic`: deterministic fallback for keyword/antonym contradictions
   └── `apply_verification_to_report`: labels or removes unverified claims with sentence grouping
```

## 1. Evidence and Attribution Rules

### Full Path Tracing
Never evaluate a claim in isolation or assume a claim is supported because the cited paper sounds relevant. Always trace the complete 7-step path:
1. **Citation Marker:** Confirm the marker exists in prose (e.g. `[1]`, `[arXiv-2405.04434]`).
2. **Resolved URL:** Confirm the marker maps to an exact URL in the report's bibliography.
3. **Evidence Record:** Confirm the URL was captured in `EvidenceStore` with `RetrievalStatus.FULL_TEXT`.
4. **Selected Passage:** Inspect the exact 1,200-character passage selected by `find_passage_for_url_and_query`.
5. **Claim Clauses:** Decompose the sentence into atomic propositions.
6. **Entity & Terminology Checks:** Ensure critical entities and acronyms are grounded in the passage.
7. **Final Verdict:** Confirm whether the passage directly entails the proposition.

### Clause-Level Substantive Evaluation
- **Compound Claims:** A single sentence often asserts multiple facts (e.g., *"Method X improves throughput by 20%, whereas Method Y suffers quadratic memory complexity"*).
- **Independent Validation:** Every substantive clause must be evaluated separately. If the source proves clause 1 but does not mention clause 2, the claim must be classified as `INSUFFICIENT_EVIDENCE`.
- **No Joint Generalization:** A source supporting one clause NEVER establishes an entire compound claim.

### Specificity & Baseline Requirements
Evidence must substantiate the exact assertions made:
- **Numerical Metrics:** Asserting *"achieves 85.2% accuracy"* requires the passage to contain 85.2% (or equivalent exact measurement).
- **Comparison Baselines:** Asserting *"outperforms PPO by 12%"* requires both the delta and the explicit baseline (PPO) in the source text.
- **Qualifiers & Modality:** Pay strict attention to qualifiers (e.g., *"under certain conditions"*, *"theoretically"*, *"consistently"*). If a claim asserts an absolute fact while the source states it as an unproven conjecture, flag it.

### Non-Entailment Indicators
Never treat the following as proof of support:
- Title or abstract match alone.
- Keyword overlap or shared domain terminology.
- Topic relevance (e.g., both paper and claim discuss Direct Preference Optimization).
- Presence of the URL in the bibliography.

### Explicit Handling of Degraded Evidence
- If a source returned `404 Not Found`, timeout, or truncation, mark it explicitly as `INSUFFICIENT_EVIDENCE` with the retrieval status noted.
- Never substitute assumptions or external general knowledge for missing evidence.

## 2. Verification Integrity & Rigor

### Zero Threshold Dilution
- **Never weaken verification criteria:** Do not lower overlap thresholds, bypass entity checks, or prompt the LLM to be "lenient" to artificially boost the supported-claim percentage.
- A research system that reports fewer claims with 95%+ precision is vastly superior to one reporting many claims with 70% precision.

### Dual-Direction Testing
When adjusting verifier logic:
1. **False-Rejection Tests:** Verify that legitimate synonyms, paraphrased clauses, and expanded passages are correctly classified as `SUPPORTED`.
2. **False-Support Tests:** Verify that subtly invalid claims, unmentioned metrics, different methods sharing vocabulary, and off-topic citations remain strictly `INSUFFICIENT_EVIDENCE` or `CONTRADICTED`.

### Preservation of Core Semantic Logic
- **Clause-Ordering Invariance:** Rhetorical reordering (e.g., active vs. passive voice, switching dependent clause positions) must not trigger false contradiction verdicts.
- **Genuine Contradictions:** Refutations, opposite empirical trends, or contradictory findings must be classified as `CONTRADICTED` and given precedence over `INSUFFICIENT_EVIDENCE`.
- **Acronym Grounding:** Distinguish citation markers from technical acronyms (e.g., `[MRR]`, `[nDCG]`, `[DPO]`).

### Failure Root-Cause Categorization
When diagnosing an unverified claim, rigorously identify the exact layer:
1. **Retrieval Failure:** Source could not be fetched or full text was missing.
2. **Passage Selection Failure:** Source text contains the answer, but the 1,200-char window selected an irrelevant section.
3. **Entity/Tokenizer Mismatch:** The claim and passage discuss the same fact, but rigid regex or token filters rejected it.
4. **Genuinely Unsupported Claim:** The author wrote a claim not substantiated by the cited document.
5. **Model / Prompt Error:** The LLM judge misread the passage or hallucinated a contradiction.

## 3. Benchmark & Audit Integrity

### Benchmark Immutability
- Preserve all historical benchmark datasets, research outputs, and evaluation reports (`phase2t5_*`, `phase2u_*`, etc.).
- Never overwrite past benchmark results with new runs. Compare against historical baselines using new, timestamped artifacts.

### Audit Transparency & Independence
- **Human / Auditor Verdicts vs. Automated Verdicts:** Always keep auditor judgments separate from pipeline outputs.
- **Blind vs. Informed Auditing:** Explicitly disclose whether an audit was conducted blind (without seeing the verifier's verdict) or informed.
- **Audit Grounds:** For every audited claim, record:
  - Exact claim text and citation marker.
  - Resolved source URL.
  - Selected passage text.
  - Specific supported/unsupported clauses.
  - Detailed audit rationale.

## 4. Hard Project Constraints

1. **Mesh API Only:** Every LLM call must use the configured Mesh API provider and model (`gemini-3.5-flash-lite` via `https://api.meshapi.ai/v1`). Never introduce fallback providers, alternative endpoints, or unauthorized credentials.
2. **Git Hygiene:** Preserve all existing staged, unstaged, and untracked work. Never run `git add .`, `git add -A`, blanket staging, resets, checkouts, or discards.
3. **Delivery-Phase-Aware Priorities:**
   - Prioritize the currently authorized project milestone.
   - During the current delivery phase, finish and verify backend-to-frontend integration before optional research-engine improvements.
   - When modifying `research_crew/`, preserve strict evidence-verification criteria.
   - Never weaken verification thresholds or standards to improve supported-claim percentages.
   - Do not modify the research engine during frontend integration unless a concrete integration blocker is identified and explicitly authorized.
